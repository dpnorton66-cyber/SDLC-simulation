AI agents across the delivery lifecycle

An agile team of eight works in two-week sprints. Place AI agents in the stages of the lifecycle and see where work flows, where it piles up, and what people spend their time on once the agents arrive.

  1. Pick a scenario, or drag an agent onto a stage.
  2. Press Play.
  3. Watch where work piles up and where agents wait.
  4. Click a stage to see what people now focus on.
  5. Move agents until the work flows.

What to look for

  1. Agents in one stage move the problem. Put coding agents in Build only. Build becomes faster, but Review becomes the slowest stage, and agent-written code takes longer to review and test. The team finishes fewer items than before, and each costs about a fifth more.
  2. The team only gains what its slowest stage gains. Build is set to +60%, yet Balanced finishes about 12 items a sprint, not 16. Review is set to +40% and has 15% more work per item from agent-written code, so it can take only about 12 a sprint, and that sets the pace for everyone.
  3. Enough agents, not more. Each agent supports two people. Build needs two agents before all three developers get the gain; a stage with one person needs one. Agents beyond that have no one to support.
  4. Spare time appears where agents work. Click a stage with agents. Routine drafting moves to the agents; deciding, judging and checking stays with people, and some tasks are new.
  5. Balance beats volume. Balanced gives every person from Analysis to Test agent support with six agents. Agents everywhere uses 18 and finishes exactly the same, with nothing piling up, so on the board it looks just as good. But its agents are busy about one day in five, each item costs about a fifth more than in Balanced, and the business view shows almost no net gain.

Work and planning

Model assumptions
  • Team. Eight people, each assigned to one stage so that the flow is visible: Analysis 1, Design 1, Build 3, Review 1, Test 1, Release 1. Each item needs 7.5 person-days: 1, 1, 3, 1, 1 and 0.5 in the six stages. Without agents the team finishes about 10 items a sprint, with Release as the only stage with spare capacity.
  • Sprints. Ten working days. By default the team plans on its recent velocity (10 items to begin with), then takes on more items during the sprint whenever Analysis has capacity and fewer than two items are waiting in total further down the line. The team therefore grows into any capacity the agents create, but stops taking work on as soon as a queue starts to form. Other planning rules are available in Simulator settings. Unfinished items carry on into the next sprint.
  • What agents do. Each stage has a productivity gain: the extra work a person in that stage gets through each day with agent support, after the time spent checking what the agents produce. Defaults are Analysis +40%, Design +30%, Build +60%, Review +40%, Test +50% and Release +40%, set in Simulator settings. Each agent supports two people; people without agent support work at the old rate. The gain is expressed as an increase in productivity, so a 50% cut in the time a task takes counts as +100%.
  • Evidence for the gains. Published figures are mostly for individual coding tasks and are usually reported as time saved. Converted to productivity: McKinsey's 2023 study found time savings of 45–50% for documentation (+82% to +100% productivity), 35–45% for writing new code (+54% to +82%), 20–30% for refactoring (+25% to +43%) and under 10% for high-complexity tasks (under +11%). GitHub's 2023 experiment found a defined coding task done in 56% less time (+126%). METR's 2025 randomised trial found experienced open-source developers took 19% longer with AI tools (about −16%). The 2024 DORA report associated a 25% rise in AI adoption with a 2.1% rise in individual productivity. Stage defaults sit below the task-level figures because every stage also contains complex work and checking.
  • Agent-written code. When Build uses agents, review and test effort per item rises by 15%. This is a judgement, in line with the 2024 DORA report's finding that higher AI adoption was associated with an estimated 7.2% fall in delivery stability.
  • Cost. Each person costs £600 a day, fully loaded, so the team costs £48,000 a sprint and about £4,800 an item without agents. Each agent costs £100 a day to run whether busy or not, covering licences, platform, monitoring and security review, plus £50 of usage for each day it spends supporting a busy person, so up to £100 more a day when it supports two. Published figures vary widely: Anthropic reports about $13 per developer per active day for assisted use, heavy agentic use runs to $500–$2,000 per engineer a month, and a 2026 Gartner Peer Insights survey found 23% of technology leaders spending $200–$500 per developer a month on coding-agent tokens and 6% over $2,000. Seat and token costs are often only part of the full cost once platform and security work are included. The defaults sit towards the heavy end because these agents run autonomously all day.
  • Business view. Each run is compared with the same team and project with no agents, simulated under the settings that run used; runs with different settings are grouped separately. A quarter is six two-week sprints. Value delivered is items finished times the value of one item, which is a setting because it differs by organisation; every item is treated as worth the same. Net gain is extra value less extra spend. Return on agent spend is net gain divided by spend on agents.
  • Item size. Items vary in size, so some take much longer than average and others much less. By default the variation is low: most items fall within about a third either side of the average. Variation makes queues form even in a well-balanced team, so the team without agents finishes a little under 10 items a sprint and some work waits. Each item's size is fixed, so every run and every scenario faces the same items. Set the variation to none in Simulator settings to see the average behaviour only.
  • Starting point. Every run starts with the team already working steadily without agents, with work in progress in every stage. Sprint 1 therefore shows the change as the agents arrive, and every sprint counts in the averages.
  • Flow. The model works in quarter-day steps. An item moves at most one stage a step, and a person gives each item at most a quarter of a day per step, so a person who finishes early moves on to the next item. Work is taken in arrival order.
  • Not modelled. Defects that reach users, rework, people moving between stages, learning over time, and differences between items.
  • Use. The numbers are for discussion, not forecasting. The pattern is what matters: where the constraint sits, and how people's work changes.
